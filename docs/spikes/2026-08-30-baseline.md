# Baseline: pre-refactor build cost

Measured on WSL2 desktop, 12 cores, 45 GB RAM, 2026-08-30, against the
pre-refactor Dockerfile (from-source Boost via `Dockerfile.boost` +
`boost-provider` stage, `deb-collector` stage).
**The pre-refactor build did not complete** — see "Finding" below.

Source of the timing: local build, but the underlying log for that build
was subsequently overwritten by a second attempt (itself cancelled before
finishing) before it could be saved anywhere durable. The timing and
error-text figures below were read live off that first, now-gone log and
transcribed into this document — they are not re-derivable from anything
that currently exists on disk. **Read "Evidentiary status of the claims in
this document" immediately below before treating any number here as
independently checkable.**

## Finding: the pre-refactor state does not build

A cold (`--no-cache`) build of the committed `Dockerfile` against the
untracked `Dockerfile.boost`, exactly as both exist in this worktree, was
observed to fail before producing a runtime image. It reached `[100%]` of
the RDKit `make` step and then failed linking the `gaExample` binary with
an undefined reference to `boost::program_options`. **The quotes below are
transcribed from the original run's log, which no longer exists on disk —
see "Evidentiary status", above; they are reported, not independently
reproducible from anything currently in this repository or its build
artifacts.** Representative linker errors (there were dozens; a few are
enough to show the shape of the failure):

```
/usr/bin/ld: CMakeFiles/gaExample.dir/GaExample.cpp.o: in function `boost::program_options::validation_error::~validation_error()':
GaExample.cpp:(.text._ZN5boost15program_options16validation_errorD2Ev[...]+0x3): undefined reference to `vtable for boost::program_options::error_with_option_name'
/usr/bin/ld: GaExample.cpp:(.text.startup+0x3e3): undefined reference to `boost::program_options::options_description::m_default_line_length'
/usr/bin/ld: GaExample.cpp:(.text.startup+0x447): undefined reference to `boost::program_options::options_description::add_options()'
```

`make` runs in parallel, so the individual link failure above scrolls past
long before the build actually stops; the top-level `all` target only
reports failure once every other parallel job has drained, at the very end
of the log:

```
#16 1113.3 make: *** [Makefile:166: all] Error 2
#16 ERROR: process "/bin/sh -c make" did not complete successfully: exit code: 2
------
 > [builder  9/11] RUN --mount=type=cache,target=/tmp/rdkit-build,id=rdkit-build,uid=999,gid=999     make:
------
Dockerfile:114
--------------------
 113 |     WORKDIR ${BUILD_DIR}
 114 | >>> RUN --mount=type=cache,target=/tmp/rdkit-build,id=rdkit-build,uid=999,gid=999 \
 115 | >>>     make
 116 |     RUN --mount=type=cache,target=/tmp/rdkit-build,id=rdkit-build,uid=999,gid=999 \
--------------------
ERROR: failed to solve: process "/bin/sh -c make" did not complete successfully: exit code: 2
```

A reader looking for "the error" at the end of the log will find only this
generic `Error 2` / exit-code-2 wrapper — the actual cause is the
`program_options` linker errors earlier in the same step's output, not
anything near this final summary.

**Root cause — and this part does not depend on the lost log.** Two facts,
both independently checkable right now (see "Evidentiary status", above),
are sufficient on their own to establish that the pre-refactor tree cannot
build, regardless of whether the transcribed failure output above is
trusted:

1. `Dockerfile.boost` declares

   ```
   ARG BOOST_LIBS_TO_BUILD=iostreams,regex,serialization,system
   ```

   — `program_options` is not in that list, so the from-source Boost image
   this Dockerfile produces never builds `libboost_program_options`.
2. RDKit's own build configuration links its `gaExample` target (built
   whenever `RDK_BUILD_PGSQL`/the default target set is built, as it is
   here) against `Boost::program_options`. A Boost install missing that
   library therefore cannot satisfy RDKit's own link step for that target
   — independent of any specific run's log.

`main`'s history contains a commit that specifically fixed the omission
(`fba509a fix: build program_options boost lib`), confirming this is a
known, previously-fixed problem that the wip `Dockerfile.boost` in this
worktree does not carry.

This is direct, empirical evidence for R2 (swap from-source Boost for
Debian's `libboost1.81-dev` package): the failure exists only because the
from-source build is a hand-maintained, incomplete enumeration of which
Boost libraries to compile. Debian's `libboost1.81-dev` family ships every
Boost library, including `program_options`, as a single package — "which
Boost libraries do we compile" stops being a question that can be gotten
wrong once Boost comes from `apt` instead of from source.

## Measured cost of the pre-refactor RDKit compile

**Not independently reproducible — see "Evidentiary status", above.** The
figures in this section were read live during attempt 1's build and
transcribed afterward; the log they came from was later overwritten by a
cancelled second attempt, so there is nothing on disk today to re-derive
them from.

| pair | PostgreSQL 17.2 / RDKit 2024_09_5 |
| --- | --- |
| wall clock to `[100%]` of `make`, then link failure | 1191 s |
| `NUM_BUILD_CORES` | 4 |
| `MAKEFLAGS` | `-j4 -l12` |
| BuildKit cache | cold (`docker build --no-cache`) |
| runtime image produced | **no** |

1191 s is a **lower bound on a full pre-refactor build, not a completed
build** — but a tight one. The failure surfaces at `[100%]`: every RDKit
object had already compiled and `make` had already reported
`Built target testCIPLabeler` before the `gaExample` link failed, so the
1191 s figure covers essentially the entire compile. Only the final link
of one *example* binary, `make install`, `pgsql_install.sh`, the
`deb-collector` stage, and the `runtime` stage's own layer cost are
missing from it — which is what makes it a meaningful lower bound rather
than a partial number. No pre-refactor runtime image was produced at any
point in this investigation with the as-committed `Dockerfile.boost`.

## Why `-j4 -l12`

`ARG MAKEFLAGS='-j${NUM_BUILD_CORES}'` in the `Dockerfile` is exported into
the build environment and is picked up by every recursive invocation of
`make` that CMake's generated build system spawns, with no shared
jobserver coordinating them. Because the recursion multiplies `-j` at each
level rather than sharing one job pool, a naive `NUM_BUILD_CORES=10` does
not mean "10 parallel jobs" — it means roughly 10 jobs *per level of
recursion*. An earlier attempt at `NUM_BUILD_CORES=10` on this 12-core host
drove load average to 223 (a live `uptime` reading at the time — not
reproducible from any surviving log; see "Evidentiary status", above) and
had to be killed; it was not a usable measurement.

The value used for the 1191 s figure above is `NUM_BUILD_CORES=4` plus an
explicit `--build-arg MAKEFLAGS='-j4 -l12'`, where `-l12` is a load-average
cap (GNU Make's `-l` flag: don't start new jobs when load average exceeds
this) that is what actually contains the nested-make explosion regardless
of how many `-j` multiply together. **Any later timing comparison against
this number must use the identical `NUM_BUILD_CORES=4` /
`MAKEFLAGS='-j4 -l12'` pair, or the ratio is meaningless.**

## R7 acceptance threshold (SPEC 4.7)

R7 requires a cartridge-only rebuild to be at least 5x faster than a full
build. This baseline document does **not** set that threshold. The
pre-refactor full build never completed (see Finding, above), and even if
it had, using it as the denominator would be the wrong choice: a
pre-refactor full build includes a from-source Boost compile that Task 17's
post-refactor build no longer has to do, which would inflate the
denominator and make the 5x gate artificially easy to pass. The honest
denominator is a full build of the **post-refactor** Dockerfile that Tasks
5/9/12 produce. Task 17 measures that build directly and derives the R7
threshold from it.

## Boost image note

`boost:bookworm-1.85.0` on this host was rebuilt during this investigation
with `BOOST_LIBS_TO_BUILD` locally patched to include `program_options`
(to test whether the link failure above was the only blocker). That local
image **now includes `program_options`** and so differs from what the
committed `Dockerfile.boost` — `BOOST_LIBS_TO_BUILD=iostreams,regex,serialization,system`,
confirmed restored to its original, unpatched contents after this
investigation — would produce if rebuilt from scratch. Anyone re-running
this baseline, or any later task that expects `boost:bookworm-1.85.0` to
match the committed `Dockerfile.boost`, should rebuild it locally first
rather than trusting the tag already on this host.
